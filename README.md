# Binance Wave Rider 🧪

> التشغيل الأمامي الحالي: شموع مغلقة5 دقائق على70 زوجًا؛ المؤشرات20/50/200 تُحسب بعدد الشموع، وحجم24 ساعة وهبوطBTC خلال ساعة يحتفظان بمدتهما الزمنية. أُلغي اشتراطBTC فوقSMA200 لشراء العملات الأخرى. بقي مانع هبوطBTC بنسبة2.5% أو أكثر خلال ساعة وشروط كل عملة. النتائج التاريخية السابقة لا تختبر هذا التعديل.

> **تحديث 8 أكتوبر 2026:** جرى اختبار ست قواعد على 771,072 شمعة. لم تتأهل أي منها بعد التكاليف. أضيفت «موجة اليوم» كتجربة سابعة: اختراق ثم أول تراجع ثم تأكيد، مع إغلاق يومي وإرسال صفقاتها لتلغرام. لم تثبت ربحيتها تاريخيًا أيضًا. [قواعدها ونتائجها](DAY_WAVE_REPORT.md). التشغيل يقارن سبع محاكاة أمامية منفصلة بفاصل 5 دقائق على أعلى70 زوجUSDT مؤهل حسب السيولة، مع إظهار العدد الفعلي إن قل المتاح. نتائج الثمانية أزواج التاريخية لا تعمم على التوسع. ويمنع الدخول الجديد للمحفظة الأساسية مع استمرار مخارجها. أرسل `/strategies` في تلغرام. [النتائج والمنهج بالتفصيل](RESEARCH_REPORT.md). وصف الدقيقة الواحدة أدناه يوثق النسخة الأصلية؛ قرار التشغيل الحالي يحكمه `wave_rider/policy.json`.

نظام تداول **ورقي فقط**، يراقب Binance Spot ويرسل الصفقات والتقارير إلى تلغرام. يبدأ بمحفظة افتراضية **300 USDT** وتجربة لمدة **7 أيام**. الوصول إلى 600 هدف قياس، **ليس توقعًا أو ضمانًا**. لا توجد واجهة تطبيق، ولا مفاتيح Binance، ولا تنفيذ أوامر مالية حقيقية.

## طريقة العمل

1. يستعلم عن جميع أزواج Binance الفورية النشطة ويحدّث قائمة الإدراجات كل ساعة. يقرأ بيانات كل الأزواج كل نحو 30 ثانية؛ أي نحو 30 ثانية + زمن الاستجابة والتحليل.
2. يؤهل أزواج **USDT** ذات تداول يومي لا يقل عن 5 ملايين USDT، مع استبعاد العملات المستقرة وبعض أصول الربط. مراقبة جميع الأزواج لا تعني تحليل كل شمعة لكل زوج في كل ثانية. لا يشمل العقود الآجلة أو الرافعة.
3. يفحص آخر 100 شمعة دقيقة لما يصل إلى 20 زوجًا في الدورة: 12 من الأعلى زخمًا، و8 بالتناوب لتغطية بقية الأزواج المؤهلة. الفرص في بقية السوق قد تُكتشف متأخرة أو لا تُكتشف.
4. يستخدم **الشموع المغلقة فقط** لاكتشاف فرضيتين:
   - **اختراق بحجم:** إغلاق أعلى من قمم آخر 20 دقيقة، وحجم ≥ ضعفي متوسط آخر 20 دقيقة، وEMA9 أعلى من EMA21.
   - **عودة إلى الاتجاه:** تراجع نحو EMA9 مع بقاء الاتجاه فوق EMA21، ثم تجاوز قمة الشمعة السابقة بحجم ≥ 1.5 مرة المتوسط.
5. يرفض الشموع ذات الذيل العلوي الكبير، أو الحركة الممتدة، أو فارق bid/ask أكبر من 0.2%، أو ابتعاد السعر الحالي أكثر من 1% عن الإشارة.
6. يشتري افتراضيًا عند ask + انزلاق 0.05%، ويبيع عند bid − انزلاق 0.05%، ويحتسب رسوم 0.1% لكل جانب. الدخول محدود بـ10% من كمية أفضل ask المعروضة.
7. يحدد الوقف بمقدار ضعفي ATR14، محصورًا بين 1% و5%. يجني نصف الكمية عند ربح سعري 2R، ويرفع الوقف لتغطية تكلفة الدخول والخروج المقدرة، ثم يتتبع القمة بمسافة الوقف الأصلية. يغلق أي مركز تجاوز 6 ساعات.
8. يراقب الخروج كل نحو 5 ثوانٍ. عند فجوة السعر يحتسب التنفيذ بسعر bid الحالي، وليس بسعر الوقف الذي لم يعد متاحًا.
9. يسجل الرصيد والمراكز والصفقات والإشعارات في SQLite على قرص دائم. يستعيد التجربة نفسها بعد إعادة التشغيل، دون إعادة الرصيد إلى 300.

الاستراتيجيات قواعد قابلة للاختبار وليست «خبيرًا يعرف المستقبل». لم يثبت اختبار تاريخي ربحيتها. USDT يُعامل كوحدة الحساب، وليس دولارًا نقديًا مضمون القيمة.

## إدارة المخاطرة

| القاعدة | القيمة |
|---|---:|
| الرصيد الابتدائي | 300 USDT افتراضي |
| أقصى مخاطرة مخططة إلى الوقف لكل صفقة، شاملة تكاليف النموذج | 1% من قيمة المحفظة |
| الحد الأقصى لقيمة مركز واحد شاملة رسوم الدخول | 20% |
| أقصى عدد مراكز متزامنة | 3 |
| حد الخسارة اليومية، محققة وغير محققة | 5% |
| حد التراجع من أعلى قيمة مسجلة | 15% |
| مهلة إعادة دخول نفس الزوج بعد إغلاقه | ساعة |
| نهاية التجربة | 7 أيام من أول دورة مراقبة سليمة، أو بلوغ 600، أو حد التراجع |

عند الحد اليومي تُغلق المراكز المتاحة وتُمنع مداخل جديدة حتى يوم UTC التالي. عند نهاية الأسبوع أو الهدف أو حد التراجع يتوقف الدخول نهائيًا لهذه التجربة ويصدر تقرير نهائي بعد إغلاق المراكز. **لا انتقال تلقائي إلى التداول الحقيقي.** الفجوات والانقطاعات قد تجعل الخسارة تتجاوز الحدود المخططة؛ وقف الخسارة ليس ضمان سعر.

## تلغرام — يمكن ربطه لاحقًا

النظام يعمل بدون تلغرام، ويحفظ الإشعارات في صندوق إرسال دائم لإرسالها بعد الربط. ترتيب الرسائل زمني، ويظهر رقم ثابت لكل رسالة؛ قد يتكرر إرسال رسالة إذا توقف البرنامج بعد إرسالها وقبل تسجيل التأكيد.

1. افتح [BotFather](https://t.me/BotFather) وأرسل `/newbot`.
2. اختر اسمًا واسم مستخدم ينتهي بـ`bot`.
3. خزّن التوكن في متغير سري `TELEGRAM_BOT_TOKEN` على Railway؛ لا تضعه في GitHub أو المحادثات.
4. شغّل الخدمة ثم أرسل `/start` إلى بوتك في محادثة خاصة. يعرض رقم المحادثة فقط إذا لم يُضبط المستلم بعد.
5. أضف الرقم إلى `TELEGRAM_CHAT_ID` وأعد نشر الخدمة. المتغير يُقرأ عند التشغيل.
6. إن كان الإرسال إلى مجموعة، أضف أيضًا `TELEGRAM_ADMIN_USER_ID`؛ بدون ذلك لن تقبل أوامر من المجموعة.

| الأمر | الوظيفة |
|---|---|
| `/status` | سلامة السوق، نطاق المراقبة، حالة التجربة |
| `/report` أو `/balance` | الرصيد والنتائج والرسوم |
| `/positions` | المراكز وأسعار الدخول والوقف |
| `/pause` | منع دخول جديد مع استمرار إدارة الخروج |
| `/resume` | استئناف الدخول ضمن حدود المخاطرة؛ لا يتجاوز إيقاف نهاية التجربة |
| `/id` | رقم المحادثة والمستخدم المصرح له |
| `/help` | التعليمات |

يرسل عمليات الدخول، وجني نصف المركز، والخروج، وأسباب الصفقات، وتنبيهات انقطاع البيانات، وتقريرًا يوميًا بتوقيت UTC، وملخص النهاية. يحظر الأوامر من المحادثات غير المصرح لها ويتجاهل الأوامر القديمة بعد الانقطاع.

## تشغيل محلي

```bash
python3.12 -m venv .venv
. .venv/bin/activate
pip install -r requirements.txt
export DATA_DIR=./data
export PORT=8000
uvicorn wave_rider.app:app --host 0.0.0.0 --port "$PORT" --workers 1
```

ملف `.env.example` مرجع للمتغيرات فقط؛ الخدمة تقرأ بيئة العملية ولا تحمّل ملفات `.env` تلقائيًا. لا حاجة لمفاتيح Binance.

- `GET /healthz`: سلامة عملية المراقبة، دون كشف الرصيد. يستخدمه Railway لفحص التشغيل.
- `GET /readyz`: جاهزية البيانات الحية؛ يرجع 503 عندما تكون البيانات قديمة أو محجوبة.
- لا صفحة ويب، ولا API لتغيير المحفظة، ولا واجهة لإدخال مفاتيح تداول حقيقية.
- يمكن استخراج سجل الصفقات محليًا باستخدام `python scripts/export_ledger.py --database data/ledger.db --output trades.csv`.

## النشر في مشروع Railway جديد

1. أنشئ مشروعًا جديدًا، ثم خدمة من مستودع GitHub `salem0557/Salem-wave-rider`.
2. أضف **Volume دائمًا** إلى الخدمة وعيّن mount path إلى `/data`. لا تستخدم نسخة تشغيل ثانية أو عدة مناطق لخدمة هذه المحفظة.
3. أضف `DATA_DIR=/data` و`TRADING_MODE=paper`. يوفر Railway متغير `PORT` تلقائيًا.
4. اختر منطقة تشغيل يسمح Binance بخدمتها وفق شروطه وصلاحية حسابك. إذا ظهر 451 أو 403، يتوقف جلب البيانات لمدة ساعة ويبلغ الخطأ؛ لا توجد محاولات لتجاوز القيود أو تبديل مصادر الأسعار خفية.
5. Railway يقرأ `railway.toml` ويثبت `requirements.txt` ويشغّل عاملًا واحدًا. الخدمة ترفض التشغيل على Railway إذا لم تجد قرصًا دائمًا أو لم يطابق `DATA_DIR` موضعه.
6. أضف متغيرات تلغرام عندما تكون جاهزًا. لا حاجة لشراء نطاق أو إنشاء واجهة عامة؛ الاتصالات إلى Binance وتلغرام صادرة.
7. افحص السجلات و`/readyz` أو `/status`. سلامة `/healthz` وحدها **لا تعني** أن اتصال Binance جاهز.

القرص يحافظ على المحفظة خلال إعادة النشر. لا تحذف `ledger.db` أثناء التجربة. احتفظ بنسخة احتياطية من القرص قبل تغييرات كبيرة. إعداد Replica واحد مع قفل على ملف المحفظة يمنع تشغيل عاملين على القرص نفسه؛ القفل لا ينسق بين أقراص منفصلة.

لإعادة تجربة جديدة بعد مراجعة نتائج الأسبوع: أوقف الخدمة وصدّر السجل واحتفظ بنسخة من قاعدة البيانات، ثم استخدم قرصًا/دليل بيانات جديدًا. لا يوجد أمر تلغرام يمسح النتائج.

## التحقق والحدود

```bash
pip install -r requirements-dev.txt
pytest -q
python -m compileall -q wave_rider scripts
```

الاختبارات تغطي المحاسبة والرسوم، وانزلاق الفجوات، والوقف المتحرك، والخروج الجزئي، والحدود اليومية والأسبوعية، واستعادة المحفظة، وعدم النظر إلى الشموع المستقبلية، وتفويض تلغرام، وحفظ الإشعارات بعد فشل الإرسال، واحترام 429 و451.

هذه **محاكاة مبسطة**: ليست تنفيذًا مؤكدًا داخل دفتر الأوامر، ولا تحاكي موضع الطابور أو عمق دفتر كامل أو التنفيذ الجزئي للخروج أو جميع قيود LOT_SIZE والحد الأدنى للكمية. الرسوم والانزلاق ثوابت تقديرية قابلة للاختلاف عن الواقع. قد تفوت حركة تلمس الوقف ثم ترتد بين فحصين. توقف البيانات يمنع ملء صفقات بأسعار مختلقة، لكنه يؤخر مخارج الوقف. نتائج المحاكاة لا تثبت نتائج تنفيذ حقيقي.

لا يرسل هذا المشروع أوامر حقيقية إلى Binance. أي تطوير مستقبلي للتداول الحقيقي مشروع منفصل يتطلب مراجعة التنفيذ والمفاتيح والقيود والاختبارات وتفويضًا صريحًا.
